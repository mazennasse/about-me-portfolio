I build the parts of apps
nobody notices — until they break.

Most people experience software through a button. I live one layer beneath it — in the routes, middleware, and database queries that decide whether it actually works.

I'm a Computer Science & AI student at Cairo University, majoring in Information Systems. But most of what I understand about backend engineering didn't come from lectures. It came from building real things. Authentication systems real users logged into. E-commerce APIs handling real carts. Chat systems that had to stay in sync.

Before I settled into Node.js, I spent time on the infrastructure side. CCNA and CompTIA A+ taught me how networks actually move data — and how latency, requests, and failure really behave in real systems. I also worked with Flutter and across the full MERN stack. That gave me a full-picture understanding of applications — not just backend in isolation, but how the client actually consumes it. That's why I don't design APIs in isolation. I design them as contracts — built around how the client will actually use them.

My philosophy is simple: an API is a contract. Every endpoint should do exactly what it says, fail loudly and clearly when it can't, and never surprise the developer on the other end of the request. I'd rather ship something predictable than something impressive that breaks under load.

E-Commerce API

A backend commerce system designed to handle product inventory, cart state, and order lifecycle with strict consistency under concurrent requests.

The challenge

Design a commerce backend that guarantees correct inventory handling under concurrent checkout requests, prevents overselling, and maintains a consistent order lifecycle across all states.

System design insight

The main risk in commerce systems is not reading data — it is writing conflicts. Multiple users can modify inventory at the same time, so the system was designed around inventory as the single source of truth with strict server-side validation for every mutation.

Approach

The data model (User, Product, Cart, Order) was defined first with explicit state transitions. Business logic was isolated in a service layer to ensure predictable behavior and avoid logic duplication across controllers.

The challenge

Design a centralized authentication system that can be reused across multiple services, ensuring secure identity verification, minimal coupling, and consistent authorization rules without duplicating logic across projects.

Design decisions

Adopted a stateless authentication model using short-lived access tokens and refresh token rotation to improve security and reduce session risk. Authorization is handled through middleware to enforce consistent access control across all routes.

Architecture approach

Built as a standalone authentication service with clear separation of concerns: controllers handle request flow, services manage token logic, and middleware enforces authentication and RBAC policies.

The challenge

Design a real-time messaging system capable of handling concurrent users, ensuring message delivery consistency, persistent chat history, and reliable synchronization between WebSocket events and REST-based data retrieval.

Architecture design

Implemented a hybrid architecture where WebSockets handle real-time delivery while REST APIs ensure persistence and data consistency. Both layers share a unified service layer to avoid business logic duplication.

Design decisions

Messages are treated as persisted entities first, then broadcast as events. This guarantees that real-time communication never bypasses database integrity, and reconnecting clients always retrieve consistent state.

The challenge

Design a reservation system where availability is enforced at the API level, guaranteeing atomic booking operations and preventing race conditions under concurrent requests.

Architecture strategy

The system was designed around a single source of truth for availability, with strict server-side conflict validation. Every booking write is treated as an atomic operation to eliminate double-booking under concurrent traffic.

Design approach

I defined the full booking lifecycle upfront — pending, confirmed, cancelled — and enforced it through the service layer to ensure predictable state transitions and prevent invalid state mutations across the system.

The challenge

Design a task system that supports real-world team workflows with high query complexity, without degrading performance as data grows (tasks, projects, users, assignments). The API must avoid endpoint explosion by supporting flexible, composable filtering.

Architecture strategy

The system is built around a query-first design, where filtering logic is centralized in a reusable service layer. This avoids duplicated controller logic and ensures consistent behavior across all task queries.

Design approach

Instead of treating tasks as simple CRUD entities, the model reflects real execution flow: projects → boards → tasks → assignments. This enables natural scaling toward team-based collaboration and future feature expansion.
